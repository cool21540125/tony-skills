# 重大性: 專注在核心, 省略不必要細節

**重大 = 會改變受眾的決定.** 不會改變決定的資訊, 再正確、再相關都不重大.

重大不等於要講. 重大資訊只在受眾**還有疑問、理解有誤、或尚未套用到專案**時才講. 上下文、專案文件或配置已經顯示受眾掌握並落實的, 不再重提.
例: 討論 Grafana Loki 部署時, 文件已經清楚描述我們就是要採用 monolithic, 或實際查訪後, log 量級明顯不需要 microservices, 就不再提 microservices 部署模式.

受眾的注意力有限. 一句無關緊要的話, 會稀釋旁邊真正重要的那句. 每句話過兩道閘門:

1. **講完這句, 受眾能因此做什麼決定?**
2. **漏掉這句, 受眾會不會因而做出錯誤決定、或事後付出代價?**

「必須講」的典型:

- 會增加顯著的金錢 or 時間成本
- 資料會遺失或被靜默丟棄而難以 or 無法還原
- 選了就難回頭 or 需付出較爲慘痛的代價
- 會使系統負載大幅度攀升
- 會推翻目前討論的前提 (例: 正在討論 A 方案怎麼調參數, 但 A 方案在受眾的環境根本跑不起來)

兩關皆否 → 刪. 原始文件的刁鑽細節、與受眾環境無關的 edge case、用不到的選項、沒開的 feature flag 都屬於這類, 「順帶一提」的警告也一樣.

**檢驗**: 逐句問「刪掉這句, 受眾的決定或後果會變嗎?」. 不會變就刪.
